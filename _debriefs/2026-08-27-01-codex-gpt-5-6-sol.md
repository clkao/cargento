# Project cockpit trajectory: cycles 13–27

## Scope

This record summarizes shaping cycles 13 through 27. These 15 cycles changed the project cockpit from a dense timeline into a command briefing.

The record also summarizes the user intent from 2026-08-24 through 2026-08-28 UTC. The timeline groups related turns. It is not a transcript copy.

The source records are the stage reports, `MIRROR_ROUNDS.md`, and `PANEL_REVISION.md` on the prototype branch. `docs/design-next-ui.md` owns the shipped preview design.

## Executive trajectory

The first cycles made events and decisions readable. The next cycles separated scope, content, human notes, and derived facts.

Later cycles removed repeated text and corrected false semantic claims. The final cycles made four command facts visible: Assignment, Execution, Next, and Captain.

The final frame uses three cells in this order:

1. Assignment
2. Execution
3. Command

Evidence remains available under disclosures. Course, Decisions, and Console keep their separate meanings.

### Assignment

The Assignment cell first uses an exact workflow task at the current stage. This source gives the strongest task identity.

If that source is absent, the cell uses the best substantive root direction. It rejects acknowledgments, links, status messages, and tool corrections.

The cell does not invent an outcome, stage, or done condition. It states whether a missing stage link blocks current work.

### Execution

The Execution cell groups child work under the exact root session. It shows active, returned, and stale lifecycle states.

A returned child can lack an assignment or result. The primary row then says `handoff unavailable`.

Fresh age details stay in Evidence. A stale return stays visible because stale work can affect recovery.

### Command

The Command cell has one authority state:

| State | Meaning | Primary behavior |
|---|---|---|
| `CAPTAIN NEEDED` | An exact question, approval, choice, or revision needs the user. | Show all exact captain requests first. |
| `FO INSPECTING` | A bounded source or attribution problem remains. | Show one concrete FO action. |
| `FO CONTINUES` | No captain request or blocking evidence gap remains. | Continue the current assignment. |

The command can use `AUTHORIZE`, `ANSWER`, `CHOOSE`, `REVISE`, `APPLY`, or `INSPECT`. Each verb has one authority meaning.

### Evidence and tabs

Evidence gives the reason for a primary claim. It includes the source session, timestamp, confidence, coverage, and exact identifier.

The tabs answer different questions:

| Tab | Question |
|---|---|
| Now | What is the assignment, execution state, and next command? |
| Course | What changed the direction or result? |
| Decisions | What did the captain decide, and did the system apply it? |
| Console | What did the exact session show? |

## Decision framework

### 1. Establish scope and provenance

The system first identifies the project. An optional session selection filters evidence inside that project.

The project still owns the recovery briefing. The UI marks selected-session context so that the filter cannot change ownership silently.

### 2. Recover the assignment

The system first reads the exact current workflow task. If that task is absent, it reads the best substantive root direction.

The system excludes tool corrections and acknowledgments. A newer message does not win only because it is newer.

### 3. Classify missing information

| Class | Condition | Action |
|---|---|---|
| Recover automatically | A readable and deterministic source exists. | Show the recovered fact. Create no action. |
| FO inspect | A named source is stale, unreadable, missing, or ambiguous. | Name one bounded inspection action. |
| Captain needed | An exact request exists, or FO inspection proves a blocking choice. | Show the exact question or authority request. |

Elapsed time does not promote an FO problem into a captain request. Missing evidence is not an actor.

### 4. Bind results

A result must bind to the displayed task or source session. A newer result from another session cannot become the current result.

Unlinked output stays in Evidence or remains absent. The UI does not imply a causal pair without a binding.

### 5. Render the command frame

The primary order is Assignment, Execution, then Command. This order shows the situation before the response.

The primary frame contains the facts that change an action. Provenance and scan mechanics stay under Evidence.

### 6. Stop

The loop stops when Assignment, Execution, Next, and Captain truth are visible without Evidence. Scope and missing-source limits must remain truthful.

After that point, a style preference does not justify another cycle.

## Five-round review loop

### Instruction

1. Give each round to a fresh reviewer.
2. Give one expert lens to each reviewer.
3. Capture the current page with Playwright Chrome.
4. Give the screenshot to the reviewer.
5. Use live APIs, source, and the renderer harness to examine semantic claims.
6. Rank the findings by command risk.
7. Choose the smallest correction in the existing regions.
8. Apply the correction before the next round.
9. Run focused tests and adversarial fixtures.
10. Serve the change on candidate port 8767.
11. Capture and inspect the changed page.
12. Move the exact bytes to stable port 8766.

### Effectiveness

Fresh reviewer context reduced attachment to the prior design. Each lens found a different failure class.

Screenshots exposed hierarchy, density, and visual authority failures. The renderer harness alone did not show these failures.

Adversarial fixtures exposed false semantic claims. Examples included unrelated results, missing handoffs, and incomplete captain coverage.

Sequential corrections produced convergence. Each round started from the accepted result of the prior round.

Before-and-after screenshots made visual claims falsifiable. Stable page hashes connected each screenshot to exact served bytes.

### Weaknesses

- The loop used much time and compute. Several full suites ran under severe host contention.
- Live state changed during each review. Reviewer activity also changed the mirror that the reviewer examined.
- One screenshot showed one current state. Adversarial states still depended on renderer fixtures and shared CSS.
- Semantic selection used rules for substantive direction. These rules can fit this session better than another session.
- Existing branch failures obscured the signal from each full suite. Isolation work added more delay.
- Repeated correction can optimize small style differences after command truth is complete.
- The loop did not include a separate human usability study.
- The workflow task still lacked a durable binding. The UI recovered the assignment from operator direction.
- Some child sources did not publish assignments or results. The final UI only stated that limit.

### Stop criterion

The loop stops when the frame gives these facts inline:

1. Assignment
2. Execution
3. Next action
4. Captain state

The scope must remain clear. Missing evidence must have one owner. Evidence and the four tabs must remain reachable.

## Current limits

- The prototype remains on the local Explore branch. It is not part of the development workflow.
- Assignment recovery can use a substantive root direction when no workflow task link exists.
- The direction classifier uses bounded rules. Another project can expose a new false positive.
- Captain coverage describes named local sources. It does not prove that every external source is clear.
- Child lifecycle records can omit assignments and results. The UI cannot reconstruct absent content.
- The session origin provides read-only output. Keyboard input remains outside the authority contract.
- Browser-local human context does not move to another browser or project identity.
- Course and retained history depend on available source records and bounded windows.
- Full repository tests contain baseline and load-sensitive failures outside the cockpit changes.

## Conclusion

The trajectory changed the cockpit from an event display into a command surface. The final design does not try to show every available fact.

The primary frame shows the facts that change action. Evidence and tabs keep the remaining facts reachable.

The five-round loop was effective because every round used a new lens and applied one correction. Screenshots made the final visual reduction possible.

The loop also cost much time and compute. The stop criterion prevents that process from becoming continuous style work.
